# LHQ Learning Hub — frontend build brief

You're building the frontend for LHQ's internal staff system against an existing
Django + DRF backend (`../backend/`). This doc is the complete contract: every
endpoint, every status code, every business rule that has to be enforced in
the UI. It was generated by exercising the live backend, not read off the
source — treat it as accurate. If anything here conflicts with what the API
actually returns, the live API wins; check `http://127.0.0.1:8000/api/docs/`
(Swagger UI, backend must be running) or `/api/schema/` (raw OpenAPI) for the
current source of truth.

## Stack context

This repo (`fontend/`) is an unmodified Vite + React 19 scaffold — plain JS,
no TypeScript, no router, no HTTP client, no state library installed yet, and
`App.jsx`/`assets/` still hold the Vite starter placeholder content you should
replace. Pick vanilla, well-known choices (e.g. `react-router` for routing,
plain `fetch` wrapped in a small client module rather than pulling in axios,
React context or a minimal store for auth state) — nothing here needs a heavy
framework.

`vite.config.js` and the backend's `CORS_ALLOWED_ORIGINS` default both assume
the dev server runs on `http://localhost:5173`. The backend runs on
`http://127.0.0.1:8000` by default (`manage.py runserver`). Put the API base
URL behind an env var (`VITE_API_BASE_URL`, default
`http://127.0.0.1:8000/api`) rather than hardcoding it.

## Auth model: JWT, not cookies

There is no session/cookie auth and no CSRF token anywhere in this API. Every
authenticated request needs an `Authorization: Bearer <access token>` header.

- **Access token**: 15 minute lifetime.
- **Refresh token**: 7 day lifetime, **rotates on every use** — each refresh
  call invalidates the token you sent and issues a new one. You must persist
  the new `refresh` value from every refresh response, not reuse the original
  one. Reusing an already-rotated refresh token returns `401` with
  `code: "token_not_valid"` ("Token is blacklisted") — treat that the same as
  any other refresh failure: clear stored tokens and send the user to login.
- **Logout** blacklists the current refresh token server-side. The access
  token isn't revoked (there's no server-side access-token blacklist) — it
  simply expires on its own within 15 minutes. This is normal for JWT; don't
  try to work around it.

Build a fetch wrapper that:
1. Attaches `Authorization: Bearer <access>` to every request except login.
2. On a `401` from any endpoint *other than* login/refresh, attempts one
   `POST /api/auth/token/refresh/`, updates stored `access`+`refresh` on
   success, and retries the original request once. If the refresh itself
   fails, clear stored tokens and redirect to login.
3. Stores tokens in memory + `localStorage` (or similar) — there's no cookie
   mechanism doing this for you.

## Data shapes

### User object (what every endpoint below returns for a user)

```jsonc
{
  "id": 1,
  "email": "wanangwa@lhq.test",
  "full_name": "Wanangwa",
  "phone": "",
  "role": "OWNER",                 // "TUTOR" | "ADMIN" | "OWNER" | "SYS_ADMIN"
  "employee_id": null,             // string or null, unique when set
  "employment_type": "",           // "" | "FULL_TIME" | "PART_TIME" | "CONTRACT"
  "address": "",
  "start_date": null,              // "YYYY-MM-DD" or null
  "is_active": true,
  "date_joined": "2026-08-20T12:00:00Z",
  "last_login": null,              // ISO datetime or null
  "tutor_profile": null,           // null, or { "id": 4, "hourly_rate": "40.00", "is_available": true,
                                   //   "can_take_new_students": false }  (read-only flag, see "Tutors and subjects")
  "teaches": false,                // true iff tutor_profile exists — independent of role
  "is_staff_level": true           // true for ADMIN / OWNER / SYS_ADMIN, false for TUTOR
}
```

Every field on this object is **read-only** in the sense that the read
serializer marks them so — writes go through the separate create/update
request shapes below, which accept a narrower field set.

`role` and `employment_type` values are exactly the uppercase strings shown
above — send and compare them as-is, don't title-case or transform them.

## Endpoints

Base path for all of these: `{VITE_API_BASE_URL}` (i.e. `/api/...`).

### `POST /auth/login/`

Public. Body: `{ "email": string, "password": string }`.

- **200**: `{ "access": "...", "refresh": "...", "user": <User object> }`
- **401**: `{ "detail": "Invalid email or password." }` — same message for
  wrong password, unknown email, *and* a correct password on a deactivated
  (`is_active: false`) account. Don't try to distinguish these in the UI;
  the backend deliberately doesn't.

### `POST /auth/token/refresh/`

Public (but pointless without a valid refresh token). Body:
`{ "refresh": string }`.

- **200**: `{ "access": "...", "refresh": "..." }` — **both** fields are new;
  persist both.
- **401**: `{ "detail": "...", "code": "token_not_valid" }` — refresh token
  expired, malformed, or already used/blacklisted.

### `POST /auth/logout/`

Requires auth. Body: `{ "refresh": string }` (the current refresh token).

- **204**: no body.
- **400**: `{ "refresh": ["Invalid or expired refresh token."] }`
- **401**: not authenticated (missing/expired access token).

### `POST /auth/setup-password/`

Public. This is the token-based "set your initial/reset password" endpoint.
Body: `{ "uid": string, "token": string, "new_password": string }`.

- **204**: no body. Password is set; user can now log in normally.
- **400**: `{ "non_field_errors": ["Invalid setup link."] }` (bad uid/token),
  `{ "non_field_errors": ["Invalid or expired setup link."] }` (token
  doesn't check out), or `{ "new_password": ["...", ...] }` (fails Django's
  password validators — multiple messages possible).

**No email is sent yet.** There is currently no way for a UI flow to obtain a
valid `uid`/`token` pair for a newly-created user — that only exists once
email sending is built. Build the form/page for this endpoint anyway (it's a
real, tested endpoint), but don't wire a "forgot password" link to it that
assumes an email will arrive; flag that gap rather than faking it.

### `GET /me/`

Requires auth. No params.

- **200**: `<User object>` for the caller.
- **401**: not authenticated.

Use this after login/refresh (or on app load with a stored token) to
rehydrate who's logged in and drive role-based UI.

### `GET /users/`

Requires auth. Paginated (`?page=N`, page size 20).

- **200**:
  ```jsonc
  { "count": 3, "next": null, "previous": null, "results": [<User>, ...] }
  ```
  For a `TUTOR`, `results` is always `[]` (`count: 0`) — this is **not** a
  403; the list is legitimately empty for them. Don't render an error state
  for an empty list here, render "no users" (or just don't show this view to
  Tutors at all — see permission matrix below).
- **401**: not authenticated.

### `POST /users/create/`

Requires auth. This is account creation — **there is no public self-register
endpoint anywhere in this API by design.** Only an already-authenticated
staff member can create another account.

Body:
```jsonc
{
  "email": "new@lhq.test",
  "full_name": "New Person",
  "role": "TUTOR",                       // required
  "phone": "",                           // optional
  "employee_id": null,                   // optional
  "employment_type": "",                 // optional
  "address": "",                         // optional
  "start_date": null,                    // optional
  "tutor_profile": { "hourly_rate": "40.00", "is_available": true }  // optional, see below
}
```

- **201**: `<User object>` for the new account. It has no usable password —
  see the setup-password note above.
- **403**: `{ "detail": "You do not have permission to create this role." }`
  — this fires if `role` is **missing or invalid too**, not just when it's a
  disallowed-but-valid role. A blank/omitted `role` on this endpoint is a
  403, not a 400 — the permission check runs before field validation. Make
  `role` a required field in your form so this never surfaces to a real
  user.
- **400**: `{ "field": ["message", ...] }` for anything else (bad email
  format, duplicate email, employee_id collision, etc).

`tutor_profile` behavior: if `role` is `"TUTOR"`, a `TutorProfile` is always
created automatically (with defaults if you don't send `tutor_profile` at
all). If `role` is something else but you *do* send `tutor_profile`, one is
still created — this models a non-Tutor (e.g. an Owner) who also teaches.
Don't show the tutor-profile fields (hourly rate, availability) in the create
form unless the selected role is Tutor, or the user has explicitly indicated
"this person also teaches."

### `GET /users/{id}/`

Requires auth.

- **200**: `<User object>`. Any staff-level user (`is_staff_level: true`) can
  view **any** account. A non-staff user (Tutor) can only view their own —
  use `/me/` for that instead of this endpoint in practice.
- **404**: `{ "detail": "Not found." }` — either the id genuinely doesn't
  exist, or the caller is non-staff and it isn't their own id. These two
  cases are deliberately indistinguishable (a Tutor querying someone else's
  id shouldn't learn whether that id exists).
- **401**: not authenticated.

### `PATCH /users/{id}/`

Requires auth. Partial update — send only the fields you're changing.

**Who can edit whom** (`has_staff_scope_over`):
| Actor | Can edit |
|---|---|
| `SYS_ADMIN` | anyone |
| `OWNER` | anyone |
| `ADMIN` | Tutors only |
| anyone | **themselves** (see narrower field set below) |

**Which fields**, once the "who" check passes:
- Staff editing someone by authority above: `full_name`, `phone`,
  `employee_id`, `employment_type`, `address`, `start_date`, `role`,
  `is_active`, `tutor_profile`.
- Self-edit (editing your own record without staff authority over
  yourself, i.e. a Tutor editing themselves): only `full_name`, `phone`,
  `address`. **`role` and `is_active` are never self-editable, for anyone.**
  Only show those two fields on an admin-facing edit form, never on a
  "my profile" self-edit form.

**Role-escalation guard**: even a staff editor who's otherwise allowed to
touch the `role` field can't set it to a role they wouldn't be allowed to
*create* (same `can_create_role` matrix as the create endpoint, see below).
E.g. an Admin editing a Tutor can change most fields but a PATCH with
`{"role": "ADMIN"}` on that Tutor still 403s — Admins can only ever produce
Tutors, whether creating or promoting.

Responses:
- **200**: updated `<User object>`.
- **404**: the actor can't even *view* this id (same rule as GET) — e.g. a
  Tutor targeting anyone but themselves.
- **403**: the actor can view the record (it exists, they're staff-level or
  it's their own) but isn't allowed to *edit* it — e.g. an Admin targeting an
  Owner, or the role-escalation case above.
  `{ "detail": "You do not have permission to edit this user." }` or
  `{ "detail": "You do not have permission to assign this role." }`.
- **400**: `{ "field": ["You cannot edit this field."] }` for any field name
  outside the actor's allowed set (e.g. a Tutor sending `role` or
  `is_active` at all — even attempting it is a 400, not silently ignored),
  or normal serializer validation errors for the fields that were allowed.

There is **no DELETE** on users — accounts are deactivated
(`PATCH { "is_active": false }`), never removed. Don't build a delete-user
UI; build a deactivate toggle instead, gated by the same edit permission
rules above.

## The role model, in full

```
Role rank (low → high): TUTOR < ADMIN < OWNER < SYS_ADMIN
```

`SYS_ADMIN` is the system owner's own role for API/admin access — not a
role LHQ staff get assigned day to day, but the API doesn't hide it or treat
it specially in list/detail views, so don't assume it can't appear in
`/users/`.

**`can_create_role(creator, target_role)`** — governs `POST /users/create/`
and role changes on `PATCH /users/{id}/`:

| Creator role | Can create/assign |
|---|---|
| `SYS_ADMIN` | any role, including `OWNER` and another `SYS_ADMIN` |
| `OWNER` | `ADMIN`, `TUTOR` |
| `ADMIN` | `TUTOR` only |
| `TUTOR` | nobody |

Use this exact matrix to filter the role `<select>` options on the create
form and on any role-change control, keyed off the logged-in user's own
role (from `/me/`). Don't just hide the "create user" button for disallowed
roles — the dropdown itself should only ever offer roles the current user is
actually allowed to assign, so a valid-looking form never produces a 403.

**UI visibility**: show a "create user" affordance to anyone with
`is_staff_level: true` (Owner, Admin, SYS_ADMIN); hide it entirely for
Tutors. Same for the users-list page — Tutors get nothing useful there
(always an empty list), so don't route them to it.

**`teaches`** (whether a `tutor_profile` exists) is independent of `role`.
An Owner or Admin can have `teaches: true`. Don't assume "teaches" implies
"is a Tutor," and don't assume `role === "TUTOR"` implies a populated
`tutor_profile` in every historical record — check `teaches`/`tutor_profile`
directly when deciding whether to show hourly-rate/availability UI.

## What's deliberately not built yet — don't assume it exists

- **No self-registration.** There will never be a public sign-up form for
  this app; every account is created by an existing staff member.
- **No email sending.** `setup-password` is live but unreachable from a
  real onboarding flow until email exists — don't build a "check your email"
  screen that promises something that won't happen.
- **No per-subject pay.** A tutor has one `hourly_rate` on `tutor_profile`.
- **No matching of students to tutors yet.** `can_take_new_students` is
  there for that later feature; nothing reads it yet.
- **No full user replace (`PUT`)** — only `PATCH`. Don't build a form that
  sends a full object; send only changed fields.

## Suggested build order

1. API client module: base URL from env, `Authorization` header injection,
   401 → refresh → retry-once, refresh-failure → clear tokens + redirect.
2. Auth context/store: holds `user` (from `/me/` or the login response),
   `login()`, `logout()`, derived `isStaffLevel`.
3. Login page → `POST /auth/login/`, store tokens, populate auth context,
   redirect into the app.
4. Route guarding: unauthenticated → login; role-based nav (hide
   users-list/create-user for Tutors).
5. Users list page (`GET /users/`) — table/list, pagination controls,
   "create user" button gated on `is_staff_level`.
6. Create-user form (`POST /users/create/`) — role dropdown filtered by
   `can_create_role` matrix above; conditionally show tutor-profile fields.
7. User detail/edit page (`GET` + `PATCH /users/{id}/`) — field set gated
   by whether the viewer has staff scope over the target vs. is viewing
   themselves; role/is_active fields only ever shown in the staff-scope
   case.
8. Logout wired to `POST /auth/logout/` with the stored refresh token, then
   clear local state regardless of response.
9. Setup-password page consuming `?uid=&token=` query params (shape TBD by
   you, since nothing generates this link yet) → `POST /auth/setup-password/`.

Write it test-first where it's reasonable to (component tests for the
permission-gating logic in particular — the role matrices above are exactly
the kind of logic that silently drifts if untested).

## Assessments (tutor comments on a student)

The whole of what a Tutor can do here: see the subjects they teach
(`GET /subjects/?mine=true`), see one of those subjects' roster
(`GET /subjects/{id}/students/`), and assess the students on it. Everything
else (students list and record, enrollments, enquiries, invoices, creating
subjects or users) answers 403 for a Tutor; the roster of a subject they
don't teach answers 404. The subject catalog itself is visible to everyone
(see "Tutors and subjects").

### `GET /students/{id}/assessments/`

Unpaginated array, newest first. Optional `?category=ACADEMIC|BEHAVIOURAL`
and `?subject=<id>`.

```jsonc
[
  {
    "id": 12,
    "student": 5,
    "subject": 4,
    "subject_name": "Maths",
    "author": 9,                 // user id, or null once that account is deleted
    "author_name": "Grace Banda", // snapshot taken when written, never null
    "category": "ACADEMIC",       // or "BEHAVIOURAL"
    "comment": "Strong on fractions.",
    "created_at": "2026-10-05T09:00:00Z"
  }
]
```

- Staff (Admin/Owner/SYS_ADMIN): any student.
- Tutor: only a student with an active enrollment in a subject they teach,
  and then the student's whole record, including other tutors' comments.
  Otherwise 404 (indistinguishable from a student that doesn't exist).

### `POST /students/{id}/assessments/`

Body `{ "subject": 4, "category": "ACADEMIC", "comment": "..." }` → 201 with
the object above. `student` and the author come from the URL and the token;
sending them in the body is ignored.

- 403 unless the caller teaches `subject` (a `TutorSubject` link) **and**
  the student is actively enrolled in it. That includes staff: an Owner who
  doesn't teach the subject can read but not write.
- 400 for a blank comment or an unknown category.
- There is no PATCH/PUT/DELETE (405). A comment stays on the record, and
  survives its subject being reassigned and its author being deleted.

UI: `/subjects/:id/students/:studentId` (`StudentAssessmentPage`) is the
tutor's view of one student; the staff student record (`/students/:id`)
shows the same list read-only. Both use
`src/components/assessments/StudentAssessments.jsx`, and
`canAssessSubject` in `src/auth/permissions.js` mirrors the write rule,
using the subject's `taught_by_me` flag.

## Company overview (Owner dashboard)

### `GET /overview/?period=this_month|last_month|this_year`

Owner and SYS_ADMIN only; 403 for Admin and Tutor. `period` defaults to
`this_month`; anything else is a 400. All sums are done server-side.

```jsonc
{
  "period": { "key": "this_month", "start": "2026-10-01", "end": "2026-11-01" }, // end is exclusive
  "counts": { "active_students": 42, "tutors": 7, "active_subjects": 9, "open_enquiries": 5 },
  "money": {
    "invoiced": "1250000.00",      // invoices created in the period
    "collected": "900000.00",      // payments recorded in the period
    "outstanding": "475000.50",    // owed as of today, whatever the period
    "overdue_amount": "120000.00", // the part of that which is past its due date
    "overdue_count": 2
  },
  "enrollment_trend": [             // six calendar months, oldest first, zero-filled
    { "month": "2026-05", "enrolled": 2, "withdrawn": 0 }
  ],
  "funnel": {                       // every enquiry, by its current stage
    "stages": [{ "stage": "INITIAL_CALL", "label": "Initial call", "count": 3 }],
    "total": 20,
    "enrolled": 15,
    "conversion_rate": 0.75         // null when there are no enquiries
  }
}
```

`active_students` is distinct students with an ACTIVE enrollment, so it is
lower than the Students list total, which also holds everyone who has left.

UI: `DashboardPage` picks one of three dashboards by role -
`OwnerDashboard` (Owner, SYS_ADMIN), the staff dashboard (Admin), or
`TutorDashboard`. `canSeeCompanyOverview` in `src/auth/permissions.js`
mirrors the backend's `IsOwnerLevel`.

## Tutors and subjects

A **subject** is a catalog entry at one **level** ("IGCSE Physics"), with
the official Cambridge topic list. Many tutors can teach a subject and a
tutor can teach many (`TutorSubject`). Each tutor also has **working hours**.
A tutor proposes changes to their own subjects and hours; nothing live
changes until staff approve. Staff can also edit any tutor directly.

Weekdays are `0` = Monday ... `6` = Sunday (all seven allowed for working
hours). Times are `"HH:MM"`. Tutor ids in `/tutors/{id}/...` are
**TutorProfile** ids (`user.tutor_profile.id`), not User ids.

### `GET /levels/`

Unpaginated, curriculum order:
`[{ "id": 3, "name": "IGCSE", "order": 3, "year_groups": [10, 11], "is_active": true }]`.
Seeded: Primary (Year 6), Lower Secondary (Years 7 to 9), IGCSE, A Level.

### `GET /subjects/`

Paginated (`count/next/previous/results`); `academicsApi.listAllSubjects`
walks every page. Any signed-in user. Filters: `?level=<id>`,
`?is_active=true|false`, `?mine=true` (subjects the caller teaches),
`?taught=true` (subjects at least one tutor teaches).

```jsonc
{
  "id": 12,
  "level": 3,
  "level_name": "IGCSE",
  "name": "Physics",
  "code": "0625",              // Cambridge syllabus code, may be ""
  "has_paper": true,           // Core and Extended papers apply
  "is_active": true,
  "taught_by_me": false,       // whether the caller teaches it
  "tutors": [{ "id": 4, "name": "Tam Tutor" }],  // STAFF RESPONSES ONLY
  "tutor_count": 1,            // STAFF ONLY: tutors who teach it
  "active_student_count": 3    // STAFF ONLY: ACTIVE student subjects on it
}
```

A tutor's response never has `tutors`, `tutor_count` or
`active_student_count`: tutors don't see who else teaches or how big a class
is. The counts are annotated in the list query (no per-subject queries).
`POST /subjects/` and `PATCH /subjects/{id}/` are staff only; `level` is
required and `name` is unique per level. `GET /subjects/{id}/` is open to
any signed-in user (catalog entry).

### `GET /subjects/{id}/topics/`

Read-only (topics come from `seed_cambridge_topics`), grouped by chapter in
syllabus order:

```jsonc
[
  { "chapter": "Number",
    "topics": [{ "id": 1, "number": "1.17", "name": "Exponential growth and decay",
                 "extended_only": true, "order": 2 }] }
]
```

The old `POST /subjects/{id}/topics/` and `PATCH/DELETE /topics/{id}/` are
gone.

### `GET` / `PUT /tutors/{id}/subjects/`

GET: staff, or the tutor themself (anyone else 404). Returns
`[{ "id", "name", "level", "level_name", "code", "has_paper" }]`.
PUT body `{ "subjects": [12, 15] }` replaces the whole set **now**, no
approval. Staff with authority over the account only (Owner/SYS_ADMIN over
anyone, Admin over Tutors); a tutor gets 403. Unknown or inactive ids: 400
`{ "subjects": ["Unknown or inactive subject id: 99."] }`.

### `GET` / `PUT /tutors/{id}/working-hours/`

Same access rules. Returns and accepts
`[{ "weekday": 0, "start_time": "08:00", "end_time": "12:00" }]`, sorted by
day then start. PUT body `{ "working_hours": [...] }` replaces the week.
A day may hold several blocks; blocks may touch but not overlap. 400 shapes:
`{ "working_hours": ["Monday 11:00 to 13:00 overlaps Monday 08:00 to 12:00."] }`,
`["Row 2: weekday must be 0 (Monday) to 6 (Sunday)."]`,
`["Friday 13:00 to 12:00: start must be before end."]`.

### Change request object

```jsonc
{
  "id": 7,
  "tutor": 4,                  // TutorProfile id
  "tutor_user": 21,            // User id, for linking to /users/{id}
  "tutor_name": "Tam Tutor",
  "kind": "SUBJECTS",          // or "WORKING_HOURS"
  "proposed": [ /* subjects as objects (like /tutors/{id}/subjects/), or hour blocks */ ],
  "note": "I can cover Physics now",
  "status": "PENDING",         // PENDING | APPROVED | REJECTED | CANCELLED
  "created_at": "2026-11-15T09:00:00Z",
  "reviewed_by_name": null,
  "reviewed_at": null,
  "reject_reason": "",
  "current": [ /* staff responses only: the tutor's live set now */ ]
}
```

### `GET` / `POST /tutors/me/change-requests/`

The caller's own requests, newest first (last 20); 404 if they have no
tutor profile. POST `{ "kind", "proposed", "note" }` → 201. `proposed` is
the **whole** new set (subject ids, or hour blocks) and is validated with
the same rules as the PUTs above. Only one PENDING request per kind: a new
one cancels the old. Staff who can review it get a notification.

### `POST /tutors/me/change-requests/{id}/cancel/`

Withdraw your own pending request → the updated object. Someone else's id:
404. Not pending: 400.

### `GET /change-requests/?status=PENDING[&tutor=<tutor profile id>]`

Staff only, unpaginated, newest first, with `current` next to `proposed`.
An Admin only sees requests from role=TUTOR accounts.

### `POST /change-requests/{id}/approve/` and `.../reject/`

Approve applies `proposed` as the tutor's new live set in one transaction,
re-validated at that moment (400 if, say, a subject was deactivated since).
Reject needs `{ "reason": "..." }` (400 if blank) and changes nothing live.
Either notifies the tutor. A request that isn't pending: 400
`{ "detail": ["This request is already approved."] }`. A rejection's
notification is short and complete ("Your working hours change was not
approved. See My Profile for the reason."); the full `reject_reason` is on
the request, shown on My Profile. Every notification is under 255
characters by design: the server refuses to store a longer one rather than
cutting it.

### `GET /notifications/` and `POST /notifications/{id}/read/`

The caller's own: `{ "unread_count": 2, "results": [{ "id", "message",
"link", "created_at", "read_at", "is_read" }] }` (the latest 20). `link` is
a frontend path. Mark-read is idempotent; someone else's id is 404.

### `tutor_can_take_new_students`

`tutor_profile.can_take_new_students` is true when the account is active,
`is_available` is set, and the tutor has at least one subject and one
working-hours block. The UI warns on a tutor's profile when subjects or
hours are missing.

UI: Subjects page (`SubjectsListPage`, grouped by level), subject detail
(topics by chapter, Extended badges), `TutorTeachingPanel` on a tutor's
profile (`/users/:id`, saves directly) and on My Profile (`/me`, sends a
change request), the review queue at `/users/change-requests`
(`ChangeRequestsPage`), and the header bell (`NotificationBell`).

## Timetable and sessions (Feature 2)

Times are local Lilongwe time (`Africa/Blantyre`), always `"HH:MM"`; dates
`"YYYY-MM-DD"`. Weekdays are 0 = Monday ... 6 = Sunday. "Tutor id" below is
the **TutorProfile** id (`tutor_profile.id`), like the Feature 1 endpoints.
Staff = ADMIN, OWNER, SYS_ADMIN. A tutor only ever reaches their own
student subjects, sessions and requests; anything else is a 404.

The old per-subject timetable slot (`subject.timetable_slot`), the
per-subject weekly lesson plans (`/lesson-plans/...`) and
`GET /students/{id}/timetable/` are **gone**. Planning moved onto each
session (`planned_topics`, below).

### Booking conflicts (409)

Creating or changing a weekly slot, moving a session, a tutor's move
request and approving a move are clash-checked against the tutor's other
sessions and weekly slots (touching edges are fine) and their working
hours. A problem answers **409**:

```jsonc
{
  "detail": "Mr Banda already teaches IGCSE Physics (Takondwa Banda) on Monday 16:00 to 17:00.",
  "code": "BOOKING_CONFLICT",
  "can_override": true,          // staff: resend with "allow_clash": true. Tutors: false.
  "warnings": [
    { "code": "CLASH", "message": "...", "items": [{ "session": 12, "slot": null, "student_subject": 3,
      "student_name": "...", "subject_name": "IGCSE Physics", "date": "2026-11-23", "weekday": 0,
      "start_time": "16:00", "end_time": "17:00" }] },
    { "code": "OUTSIDE_WORKING_HOURS", "message": "Monday 19:00 to 20:00 is outside Mr Banda's working hours.", "items": [] }
  ]
}
```

UI: show each `message` with **Cancel** and, when `can_override`, **Book
anyway** (same request plus `allow_clash: true`). See `ConflictNotice`.

### Student subject object

One student taking one subject with one tutor.

```jsonc
{
  "id": 7,
  "student": { "id": 1, "name": "Takondwa Banda", "student_number": "STU-000001" },
  "subject": { "id": 3, "name": "Physics", "level_name": "IGCSE", "display_name": "IGCSE Physics" },
  "tutor": { "id": 4, "name": "Mr Banda", "user_id": 9 },
  "topic_ids": [11, 12],          // the student's topics (default: all of the subject's)
  "planned_sessions": 24,
  "session_minutes": 60,
  "mode": "IN_PERSON",            // or "ONLINE"
  "start_date": "2026-11-16",
  "confirmed_end_date": null,     // set by confirm-end
  "status": "ACTIVE",             // ACTIVE | ENDED | CANCELLED
  "slots": [{ "id": 1, "weekday": 0, "start_time": "16:00", "end_time": "17:00" }],
  "progress": {
    "planned": 24, "held": 18, "not_held": 1, "remaining": 6, "unlogged": 0,
    "held_minutes": 1080, "held_hours": 18.0,
    "topics_covered": 9, "topics_total": 12, "covered_topic_ids": [...],
    "expected_end_date": "2026-12-10",   // null when it can't be worked out (no slots)
    "needs_end_confirmation": false,      // remaining is 0 or all topics covered, no confirmed end
    "end_reason": null                    // "SESSIONS_USED" | "TOPICS_COVERED" | null
  },
  "created_by_name": "Grace Kamanga",
  "created_at": "..."
}
```

`remaining` = planned minus Held. Not held, missed (log window closed) and
cancelled sessions don't use the plan, so one more session is generated at
the end and `expected_end_date` moves back.

### `GET` / `POST /student-subjects/`

GET: `?student=&tutor=&subject=&status=`, unpaginated; staff all, a tutor
their own. POST (staff): `{student, subject, tutor, planned_sessions,
session_minutes?, mode?, start_date, topic_ids?, slots: [{weekday,
start_time, end_time}], allow_clash?}` -> 201 with the object. The tutor
must teach the subject (400 otherwise); one ACTIVE per student and subject;
a student subject's own slots may not overlap. Sessions are generated
straight away (four weeks ahead).

### `GET` / `PATCH /student-subjects/{id}/`

PATCH (staff): any of `tutor` (only before anything is logged), `topic_ids`,
`planned_sessions` (not below Held), `session_minutes`, `mode`,
`start_date`, `status: "CANCELLED"` (removes future sessions), plus
`allow_clash`. Future scheduled sessions are regenerated; past and logged
ones are never touched.

### `POST /student-subjects/{id}/slots/`, `PATCH` / `DELETE /slots/{id}/`

Staff. `{weekday, start_time, end_time, allow_clash?}`. Answers with the
whole student subject (POST 201, PATCH 200); DELETE 204. A slot's future
sessions are regenerated (their planned topics go with them).

### `POST /student-subjects/{id}/confirm-end/` and `.../add-sessions/`

Staff. `{last_date}`: removes scheduled sessions after it and generates none
past it; the time frees up for other bookings after that date, and the
student subject becomes ENDED once it has passed. 400 if a session was held
after `last_date`. `{count}` (1-200): adds planned sessions and clears a
confirmed end (re-opens an ENDED one).

### `GET /students/{id}/subjects/`

Staff. Every student subject of that student, for the student page.

### `GET /students/` and `PATCH /students/{id}/` (Feature 2 follow-up)

Every student has `enrolled_on` (date). It defaults to today when the student
is created (the enrolment flow) and only staff can change it, with
`PATCH /students/{id}/ {"enrolled_on": "2026-09-02"}`. That is the only
editable field; a future date is a 400, and `PUT` is 405. The reply is the
full student.

`GET /students/` takes `?q=` (name or student number) and
`?ordering=-enrolled_on` (default, newest enrolment first, then name),
`enrolled_on`, `full_name` or `-full_name`; anything else is a 400. The
Students tab reads every page and groups by month from `enrolled_on`, so a
month is never split across pages.

### `GET /subjects/{id}/students/` (roster)

Who is learning the subject: one item per ACTIVE student subject (the v1
enrolments are no longer read). Each item is the usual student object plus:

```jsonc
{
  "student_subject_id": 7,
  "tutor": { "id": 4, "name": "Mr Banda" },
  "mode": "IN_PERSON",
  "slots": [{ "weekday": 0, "start_time": "16:00", "end_time": "17:00" }]
}
```

Staff see every student on the subject. A tutor sees only their own students
on a subject they teach (404 if they don't teach it). The subject page groups
the roster by tutor from the subject's `tutors` list. The assessment page
still reads this same list.

### Session object

```jsonc
{
  "id": 101,
  "student_subject": 7,
  "student": {...}, "subject": {...}, "tutor": {...},   // as above
  "mode": "IN_PERSON",
  "slot": 1,                       // null for a one-off (a moved session)
  "date": "2026-11-16", "start_time": "16:00", "end_time": "17:00",
  "status": "SCHEDULED",           // stored: SCHEDULED | HELD | NOT_HELD | CANCELLED
  "display_status": "UNLOGGED",    // + UNLOGGED (ended, still loggable), MISSED (window closed:
                                   //   counts as not held), MOVED (cancelled because it moved)
  "log_deadline": "2026-11-17T17:00:00+02:00",   // 24 hours after the end
  "can_log": true,                 // for the caller, right now
  "not_held_reason": "", "admin_note": "",
  "topics_covered": [11], "planned_topics": [12], "planned_topic_names": ["Energy"],
  "logged_by_name": null, "logged_at": null,
  "moved_from": null,              // id of the cancelled original, on a moved session
  "moved_to": null,                // {id, date, start_time, end_time} on a moved-away original
  "pending_request": null,         // change request object, below
  "latest_request": null
}
```

`GET /sessions/{id}/` adds `events` (history: `{id, action: LOG | CORRECT |
MOVE | CANCEL, actor_name, from_status, to_status, note, created_at}`),
`change_requests` (all, newest first), `topics` (the student's topics:
`{id, number, name, chapter, covered_before}`) and `moved_from_detail`.

### `GET /sessions/?from=&to=[&tutor=&student=&subject=&student_subject=]`

Both dates required, inclusive, at most 62 days apart. Unpaginated, by date
then time. Generates any sessions due in that range first. A tutor gets only
their own, whatever the filters say.

### `POST /sessions/{id}/log/`

`{held: true|false, reason?, topic_ids?, admin_note?}`. A tutor: own
session, only once it has started, only while SCHEDULED, only until 24
hours after its end. Otherwise 400 with one of: "You can log this session
once it has started.", "The logging window closed 24 hours after the
session. Ask admin to log it.", "This session is already logged. Ask admin
to correct it." Not held needs `reason`. Staff can log or correct any
session at any time; `admin_note` is then required. Every log and
correction is recorded in `events`. Logging withdraws a pending request.

### `PUT /sessions/{id}/plan/`

`{topic_ids}`: the topics a scheduled session will cover (the session's
tutor or staff). They pre-tick "topics covered" when it is logged.

### `POST /sessions/{id}/move/` and `.../cancel/`

Staff, directly. Move: `{new_date, new_start_time, new_end_time, reason,
allow_clash?}` -> 201 with the **new** one-off session (`moved_from` set);
the original becomes CANCELLED (MOVED). Cancel: `{reason}`. Only a
SCHEDULED session. The tutor is notified.

### Change request object and endpoints

```jsonc
{ "id": 5, "session": 101, "kind": "MOVE",   // or "CANCEL"
  "new_date": "2026-11-24", "new_start_time": "10:00", "new_end_time": "11:00",
  "reason": "...", "status": "PENDING",      // PENDING | APPROVED | REJECTED | CANCELLED
  "requested_by_name": "...", "created_at": "...",
  "reviewed_by_name": null, "reviewed_at": null, "reject_reason": "" }
```

- `POST /sessions/{id}/change-requests/` (the session's tutor):
  `{kind, reason, new_date?, new_start_time?, new_end_time?}` -> 201 with
  the session detail. Only a session that hasn't started, one pending
  request per session, a move must be in the future and is clash-checked
  (409, `can_override: false`). Nothing changes until approved.
- `GET /session-change-requests/?status=PENDING` - staff all, a tutor
  their own; each row adds `current: {date, start_time, end_time,
  status}`, `student`, `subject`, `tutor`.
- `POST /session-change-requests/{id}/approve/` `{allow_clash?}` (staff):
  applies it exactly like a direct move or cancel, clash-checked again.
- `POST /session-change-requests/{id}/reject/` `{reason}` (staff).
- `POST /session-change-requests/{id}/withdraw/` (the tutor, pending only).

The tutor's notifications are short ("Your request to move the Mon 23 Nov
16:00 session was not approved. Open My Timetable for the reason."); the
reason is on the request.

### `GET /tutors/{id}/free-slots/?week=YYYY-MM-DD`

Staff or the tutor. `week` is any day in it (default: this week). `{week_start,
days: [{weekday, date, working, busy, free}]}`, each list `[{start_time,
end_time}]`. Free = working hours minus every non-cancelled session and every
weekly slot still reserved for an active student subject (time frees only
after a confirmed last session).

### `GET /tutors/{id}/hours/?month=YYYY-MM`

Staff or the tutor. Default: this month. `{month, sessions_held, minutes,
hours: "6.00", hourly_rate, estimated_amount: "36000.00" | null,
is_estimate: true, sessions: [{id, date, start_time, end_time, minutes,
student_name, subject_name}]}`. Held sessions only. The amount is an
estimate at the one `hourly_rate` (per-subject rates aren't built); null
without a rate.

### Management commands (server)

- `generate_sessions [--weeks 4]`: generate sessions ahead. Idempotent, run daily.
- `remind_unlogged_sessions`: end-of-day notification to each tutor listing
  their unlogged sessions. Idempotent per day. Scheduling them on the server
  comes later.

UI: `/timetable` (staff: master timetable with filters; tutor: own week
with free time shaded), the session panel (`SessionPanel`, opened with
`?session=<id>`), `/timetable/requests` (staff queue),
`/student-subjects/new?student=<id>` (staff, reached from the student page's
"Add a subject"; there is no list page or sidebar item for student subjects),
the student page (header with enrolled-on, Subjects, Upcoming sessions,
Guardians, collapsed Session history), the Students tab (grouped by enrolment
month), the Subjects tab (Thumbnails or List, remembered per browser), the tutor dashboard (today + unlogged with countdowns),
and `TutorHoursCard` on `/users/:id` and `/me`.
