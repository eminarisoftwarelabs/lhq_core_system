# LHQ Learning Hub — frontend build brief

You're building the frontend for LHQ's internal staff system against an existing
Django + DRF backend (`../backend/`). This doc is the complete contract: every
endpoint, every status code, every business rule that has to be enforced in
the UI. It was generated by exercising the live backend, not read off the
source — treat it as accurate. If anything here conflicts with what the API
actually returns, the live API wins; check `http://127.0.0.1:8000/api/docs/`
(Swagger UI, backend must be running) or `/api/schema/` (raw OpenAPI) for the
current source of truth.

## Stack context

This repo (`fontend/`) is an unmodified Vite + React 19 scaffold — plain JS,
no TypeScript, no router, no HTTP client, no state library installed yet, and
`App.jsx`/`assets/` still hold the Vite starter placeholder content you should
replace. Pick vanilla, well-known choices (e.g. `react-router` for routing,
plain `fetch` wrapped in a small client module rather than pulling in axios,
React context or a minimal store for auth state) — nothing here needs a heavy
framework.

`vite.config.js` and the backend's `CORS_ALLOWED_ORIGINS` default both assume
the dev server runs on `http://localhost:5173`. The backend runs on
`http://127.0.0.1:8000` by default (`manage.py runserver`). Put the API base
URL behind an env var (`VITE_API_BASE_URL`, default
`http://127.0.0.1:8000/api`) rather than hardcoding it.

## Auth model: JWT, not cookies

There is no session/cookie auth and no CSRF token anywhere in this API. Every
authenticated request needs an `Authorization: Bearer <access token>` header.

- **Access token**: 15 minute lifetime.
- **Refresh token**: 7 day lifetime, **rotates on every use** — each refresh
  call invalidates the token you sent and issues a new one. You must persist
  the new `refresh` value from every refresh response, not reuse the original
  one. Reusing an already-rotated refresh token returns `401` with
  `code: "token_not_valid"` ("Token is blacklisted") — treat that the same as
  any other refresh failure: clear stored tokens and send the user to login.
- **Logout** blacklists the current refresh token server-side. The access
  token isn't revoked (there's no server-side access-token blacklist) — it
  simply expires on its own within 15 minutes. This is normal for JWT; don't
  try to work around it.

Build a fetch wrapper that:
1. Attaches `Authorization: Bearer <access>` to every request except login.
2. On a `401` from any endpoint *other than* login/refresh, attempts one
   `POST /api/auth/token/refresh/`, updates stored `access`+`refresh` on
   success, and retries the original request once. If the refresh itself
   fails, clear stored tokens and redirect to login.
3. Stores tokens in memory + `localStorage` (or similar) — there's no cookie
   mechanism doing this for you.

## Data shapes

### User object (what every endpoint below returns for a user)

```jsonc
{
  "id": 1,
  "email": "wanangwa@lhq.test",
  "full_name": "Wanangwa",
  "phone": "",
  "role": "OWNER",                 // "TUTOR" | "ADMIN" | "OWNER" | "SYS_ADMIN"
  "employee_id": null,             // string or null, unique when set
  "employment_type": "",           // "" | "FULL_TIME" | "PART_TIME" | "CONTRACT"
  "address": "",
  "start_date": null,              // "YYYY-MM-DD" or null
  "is_active": true,
  "date_joined": "2026-08-20T12:00:00Z",
  "last_login": null,              // ISO datetime or null
  "tutor_profile": null,           // null, or { "hourly_rate": "40.00", "is_available": true }
  "teaches": false,                // true iff tutor_profile exists — independent of role
  "is_staff_level": true           // true for ADMIN / OWNER / SYS_ADMIN, false for TUTOR
}
```

Every field on this object is **read-only** in the sense that the read
serializer marks them so — writes go through the separate create/update
request shapes below, which accept a narrower field set.

`role` and `employment_type` values are exactly the uppercase strings shown
above — send and compare them as-is, don't title-case or transform them.

## Endpoints

Base path for all of these: `{VITE_API_BASE_URL}` (i.e. `/api/...`).

### `POST /auth/login/`

Public. Body: `{ "email": string, "password": string }`.

- **200**: `{ "access": "...", "refresh": "...", "user": <User object> }`
- **401**: `{ "detail": "Invalid email or password." }` — same message for
  wrong password, unknown email, *and* a correct password on a deactivated
  (`is_active: false`) account. Don't try to distinguish these in the UI;
  the backend deliberately doesn't.

### `POST /auth/token/refresh/`

Public (but pointless without a valid refresh token). Body:
`{ "refresh": string }`.

- **200**: `{ "access": "...", "refresh": "..." }` — **both** fields are new;
  persist both.
- **401**: `{ "detail": "...", "code": "token_not_valid" }` — refresh token
  expired, malformed, or already used/blacklisted.

### `POST /auth/logout/`

Requires auth. Body: `{ "refresh": string }` (the current refresh token).

- **204**: no body.
- **400**: `{ "refresh": ["Invalid or expired refresh token."] }`
- **401**: not authenticated (missing/expired access token).

### `POST /auth/setup-password/`

Public. This is the token-based "set your initial/reset password" endpoint.
Body: `{ "uid": string, "token": string, "new_password": string }`.

- **204**: no body. Password is set; user can now log in normally.
- **400**: `{ "non_field_errors": ["Invalid setup link."] }` (bad uid/token),
  `{ "non_field_errors": ["Invalid or expired setup link."] }` (token
  doesn't check out), or `{ "new_password": ["...", ...] }` (fails Django's
  password validators — multiple messages possible).

**No email is sent yet.** There is currently no way for a UI flow to obtain a
valid `uid`/`token` pair for a newly-created user — that only exists once
email sending is built. Build the form/page for this endpoint anyway (it's a
real, tested endpoint), but don't wire a "forgot password" link to it that
assumes an email will arrive; flag that gap rather than faking it.

### `GET /me/`

Requires auth. No params.

- **200**: `<User object>` for the caller.
- **401**: not authenticated.

Use this after login/refresh (or on app load with a stored token) to
rehydrate who's logged in and drive role-based UI.

### `GET /users/`

Requires auth. Paginated (`?page=N`, page size 20).

- **200**:
  ```jsonc
  { "count": 3, "next": null, "previous": null, "results": [<User>, ...] }
  ```
  For a `TUTOR`, `results` is always `[]` (`count: 0`) — this is **not** a
  403; the list is legitimately empty for them. Don't render an error state
  for an empty list here, render "no users" (or just don't show this view to
  Tutors at all — see permission matrix below).
- **401**: not authenticated.

### `POST /users/create/`

Requires auth. This is account creation — **there is no public self-register
endpoint anywhere in this API by design.** Only an already-authenticated
staff member can create another account.

Body:
```jsonc
{
  "email": "new@lhq.test",
  "full_name": "New Person",
  "role": "TUTOR",                       // required
  "phone": "",                           // optional
  "employee_id": null,                   // optional
  "employment_type": "",                 // optional
  "address": "",                         // optional
  "start_date": null,                    // optional
  "tutor_profile": { "hourly_rate": "40.00", "is_available": true }  // optional, see below
}
```

- **201**: `<User object>` for the new account. It has no usable password —
  see the setup-password note above.
- **403**: `{ "detail": "You do not have permission to create this role." }`
  — this fires if `role` is **missing or invalid too**, not just when it's a
  disallowed-but-valid role. A blank/omitted `role` on this endpoint is a
  403, not a 400 — the permission check runs before field validation. Make
  `role` a required field in your form so this never surfaces to a real
  user.
- **400**: `{ "field": ["message", ...] }` for anything else (bad email
  format, duplicate email, employee_id collision, etc).

`tutor_profile` behavior: if `role` is `"TUTOR"`, a `TutorProfile` is always
created automatically (with defaults if you don't send `tutor_profile` at
all). If `role` is something else but you *do* send `tutor_profile`, one is
still created — this models a non-Tutor (e.g. an Owner) who also teaches.
Don't show the tutor-profile fields (hourly rate, availability) in the create
form unless the selected role is Tutor, or the user has explicitly indicated
"this person also teaches."

### `GET /users/{id}/`

Requires auth.

- **200**: `<User object>`. Any staff-level user (`is_staff_level: true`) can
  view **any** account. A non-staff user (Tutor) can only view their own —
  use `/me/` for that instead of this endpoint in practice.
- **404**: `{ "detail": "Not found." }` — either the id genuinely doesn't
  exist, or the caller is non-staff and it isn't their own id. These two
  cases are deliberately indistinguishable (a Tutor querying someone else's
  id shouldn't learn whether that id exists).
- **401**: not authenticated.

### `PATCH /users/{id}/`

Requires auth. Partial update — send only the fields you're changing.

**Who can edit whom** (`has_staff_scope_over`):
| Actor | Can edit |
|---|---|
| `SYS_ADMIN` | anyone |
| `OWNER` | anyone |
| `ADMIN` | Tutors only |
| anyone | **themselves** (see narrower field set below) |

**Which fields**, once the "who" check passes:
- Staff editing someone by authority above: `full_name`, `phone`,
  `employee_id`, `employment_type`, `address`, `start_date`, `role`,
  `is_active`, `tutor_profile`.
- Self-edit (editing your own record without staff authority over
  yourself, i.e. a Tutor editing themselves): only `full_name`, `phone`,
  `address`. **`role` and `is_active` are never self-editable, for anyone.**
  Only show those two fields on an admin-facing edit form, never on a
  "my profile" self-edit form.

**Role-escalation guard**: even a staff editor who's otherwise allowed to
touch the `role` field can't set it to a role they wouldn't be allowed to
*create* (same `can_create_role` matrix as the create endpoint, see below).
E.g. an Admin editing a Tutor can change most fields but a PATCH with
`{"role": "ADMIN"}` on that Tutor still 403s — Admins can only ever produce
Tutors, whether creating or promoting.

Responses:
- **200**: updated `<User object>`.
- **404**: the actor can't even *view* this id (same rule as GET) — e.g. a
  Tutor targeting anyone but themselves.
- **403**: the actor can view the record (it exists, they're staff-level or
  it's their own) but isn't allowed to *edit* it — e.g. an Admin targeting an
  Owner, or the role-escalation case above.
  `{ "detail": "You do not have permission to edit this user." }` or
  `{ "detail": "You do not have permission to assign this role." }`.
- **400**: `{ "field": ["You cannot edit this field."] }` for any field name
  outside the actor's allowed set (e.g. a Tutor sending `role` or
  `is_active` at all — even attempting it is a 400, not silently ignored),
  or normal serializer validation errors for the fields that were allowed.

There is **no DELETE** on users — accounts are deactivated
(`PATCH { "is_active": false }`), never removed. Don't build a delete-user
UI; build a deactivate toggle instead, gated by the same edit permission
rules above.

## The role model, in full

```
Role rank (low → high): TUTOR < ADMIN < OWNER < SYS_ADMIN
```

`SYS_ADMIN` is the system owner's own role for API/admin access — not a
role LHQ staff get assigned day to day, but the API doesn't hide it or treat
it specially in list/detail views, so don't assume it can't appear in
`/users/`.

**`can_create_role(creator, target_role)`** — governs `POST /users/create/`
and role changes on `PATCH /users/{id}/`:

| Creator role | Can create/assign |
|---|---|
| `SYS_ADMIN` | any role, including `OWNER` and another `SYS_ADMIN` |
| `OWNER` | `ADMIN`, `TUTOR` |
| `ADMIN` | `TUTOR` only |
| `TUTOR` | nobody |

Use this exact matrix to filter the role `<select>` options on the create
form and on any role-change control, keyed off the logged-in user's own
role (from `/me/`). Don't just hide the "create user" button for disallowed
roles — the dropdown itself should only ever offer roles the current user is
actually allowed to assign, so a valid-looking form never produces a 403.

**UI visibility**: show a "create user" affordance to anyone with
`is_staff_level: true` (Owner, Admin, SYS_ADMIN); hide it entirely for
Tutors. Same for the users-list page — Tutors get nothing useful there
(always an empty list), so don't route them to it.

**`teaches`** (whether a `tutor_profile` exists) is independent of `role`.
An Owner or Admin can have `teaches: true`. Don't assume "teaches" implies
"is a Tutor," and don't assume `role === "TUTOR"` implies a populated
`tutor_profile` in every historical record — check `teaches`/`tutor_profile`
directly when deciding whether to show hourly-rate/availability UI.

## What's deliberately not built yet — don't assume it exists

- **No self-registration.** There will never be a public sign-up form for
  this app; every account is created by an existing staff member.
- **No email sending.** `setup-password` is live but unreachable from a
  real onboarding flow until email exists — don't build a "check your email"
  screen that promises something that won't happen.
- **No Subject/TutorProfile endpoints beyond the nested `tutor_profile`
  field** on the user create/update requests above. There's a `Subject`
  model in the backend (subject-to-tutor assignment) but no REST endpoint
  for it yet — don't build a subjects UI against this API; ask if you need
  it, it isn't here.
- **No full user replace (`PUT`)** — only `PATCH`. Don't build a form that
  sends a full object; send only changed fields.

## Suggested build order

1. API client module: base URL from env, `Authorization` header injection,
   401 → refresh → retry-once, refresh-failure → clear tokens + redirect.
2. Auth context/store: holds `user` (from `/me/` or the login response),
   `login()`, `logout()`, derived `isStaffLevel`.
3. Login page → `POST /auth/login/`, store tokens, populate auth context,
   redirect into the app.
4. Route guarding: unauthenticated → login; role-based nav (hide
   users-list/create-user for Tutors).
5. Users list page (`GET /users/`) — table/list, pagination controls,
   "create user" button gated on `is_staff_level`.
6. Create-user form (`POST /users/create/`) — role dropdown filtered by
   `can_create_role` matrix above; conditionally show tutor-profile fields.
7. User detail/edit page (`GET` + `PATCH /users/{id}/`) — field set gated
   by whether the viewer has staff scope over the target vs. is viewing
   themselves; role/is_active fields only ever shown in the staff-scope
   case.
8. Logout wired to `POST /auth/logout/` with the stored refresh token, then
   clear local state regardless of response.
9. Setup-password page consuming `?uid=&token=` query params (shape TBD by
   you, since nothing generates this link yet) → `POST /auth/setup-password/`.

Write it test-first where it's reasonable to (component tests for the
permission-gating logic in particular — the role matrices above are exactly
the kind of logic that silently drifts if untested).
